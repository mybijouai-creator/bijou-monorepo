## 0. The two-property split (the thing that surprises everyone)

Bijou is not one app. It is two properties on different stacks, and the journey
crosses between them:

| Property | Host | Stack | Role |
|---|---|---|---|
| **Marketing** | `mybijou.xyz` (→ `www.`) | React 19 + Vite, Vercel | Convince, capture a lead |
| **Product** | `app.mybijou.xyz` | FastAPI serving hand-written static HTML, Fly.io | Register, onboard, operate |

The handoff between them is a **plain outbound link**, not a session transfer.
`packages/landing` has no auth, no session, and no Supabase client in the
browser bundle. Anyone modelling this as one SPA will model it wrong.

**Where:** `https://www.mybijou.xyz/` · `packages/landing/App.tsx`

`60174106981`; `WaitlistStrip` takes a bare email.

## Stage 2 — Lead capture (**not** registration)

**Where:** `components/OnboardingModal.tsx` — one modal, three modes
(`signup` | `waitlist` | `demo`).

| Field | Required | Validation |
|---|---|---|
| `business_name` | yes | trimmed length ≥ 2 |
| `email` | yes | must contain `@` and `.` (client-side only) |
| `phone` | no | digits stripped, leading `0` → `60`, then ≥ 10 digits |
| `industry` | no | 10 options: `real_estate`, `healthcare`, `fnb`, `retail`, `education`, `beauty`, `automotive`, `professional_services`, `logistics`, `other` |
| `demo_time` | demo mode only | free text, non-empty |

**All three modes POST to `/api/leads`** — which writes a Supabase `leads` row
and sends email via Resend. Demo mode additionally fires a best-effort
`POST /api/demo` whose failure is swallowed.

> **[GAP] This creates no account.** Success shows *"Check your email"* and an
> outbound link to `https://app.mybijou.xyz/signup`. The user re-enters their
> details on the other property. `api/onboarding/signup.js` exists and is
> correctly written, but **nothing calls it** — verified by grep across all
> `.tsx`.

> **[GAP] Payload mismatch.** The modal sends `business_name`; `api/leads.js:243`
> destructures `name`. It only works because the modal redundantly sends both.

## Stage 3 — Registration

**Where:** `app.mybijou.xyz/signup` → `packages/backend/static/signup.html` →
`POST /api/auth/signup` → `src/saas/auth_api.py`

Two paths, and they behave differently:

### 3a. Email + password
```
{business_name, email, phone, password, vertical}
```
Client-side: password ≥ 8, passwords match. Server-side: Supabase
`auth.sign_up` → create `tenants` row → link `tenant_users` row → send
verification email.

**Email confirmation is ON** (`mailer_autoconfirm: false`), so the response
carries **no session**. That is success, not failure:
```
AuthResponse{access_token: null, refresh_token: null, tenant_id, email_confirmation_required: true}
```
The user verifies by email, then signs in.

> **Fixed 2026-08-10.** Previously `session=None` was read as "email already
> exists" → `409` for **100% of new registrations**, leaving an orphaned
> `auth.users` row with no tenant, so the later login 404'd forever.

> **[GAP] Email rate limit.** Every signup sends a confirmation email through
> Supabase's built-in SMTP (~2–4/hour, test-grade), producing rate-limit errors
> under real traffic. Fix is custom SMTP (Resend is already wired at
> `src/saas/email_service.py`). **Not yet applied.**

### 3b. Google OAuth
`signup.html:498` → `/api/auth/google/login` → Google consent →
`/api/auth/google/callback` → `src/saas/google_oauth.py` creates the tenant
directly (no email verification step) → redirect to `/onboard/{token}`.

> **Fixed 2026-08-10.** The callback built its redirect from
> `request.base_url`, which behind Fly's proxy is `bijou-production.fly.dev` —
> a **different browser origin**. The dashboard's JWT lives in origin-scoped
> `localStorage`, so the session was invisible and the user was bounced to
> `/login` with no QR and no vertical selection.

> **[GAP] Two inconsistent Google flows.** `signup.html` uses the backend flow
> (lands on `/onboard/{token}`); `login.html:491` uses Supabase
> `signInWithOAuth` with `redirectTo=/static/auth-callback.html` (lands on
> `/dashboard`). Same button, two destinations. Should be unified.

## Stage 4 — Onboarding (WhatsApp pairing)

**Where:** `/onboard/{token}` → `static/onboard-qr.html`, polling
`/api/onboarding/status/{token}` every 3s and rendering
`/api/onboarding/qr/{token}`.

1. Scan the QR with the business WhatsApp account.
2. The Go bridge (`packages/bridge/`) pairs and begins syncing.
3. On connect, the page calls `/api/onboarding/complete/{token}` and redirects
   to `/dashboard`.

Knowledge setup continues at `/kb-wizard` (`kb-wizard.html`).

> **[GAP] Three overlapping onboarding routers exist** — `onboarding_api.py`,
> `onboarding_api_v3.py`, and `onboarding_complete.py` (prefix
> `/api/onboarding/v2`). `/onboard/{token}` is additionally registered **twice**
> (`bijou.py:5991` and `:6703`); the second is dead. Needs consolidation.

---

## Stage 5 — Session

JWT in `localStorage`: `access_token`, `refresh_token`, `tenant_id`
(`dashboard.html:329-407`), with a magic-link `?token=` / `?tenant_id=`
fallback. Expiry triggers `/api/auth/refresh`.

**Invariant:** because the session is origin-scoped, every user-facing redirect
must stay on `https://app.mybijou.xyz`. Never build one from the request host.

## Stage 6 — Dashboard (steady state)

**Where:** `/dashboard` → `packages/backend/static/dashboard.html`

Sidebar (14 items) and their data sources:

| Item | Backing endpoint | Purpose |
|---|---|---|
| Home | `/api/dashboard/stats` | Volume, escalations, response time |
| Inbox | `/conversations`, `/send-message`, `/takeover` | Live conversations; human takeover |
| Escalations | `/escalations` | What Bijou couldn't answer |
| Updates | — | Product changelog |
| Analytics | `/analytics/timeseries` | Trends |
| Knowledge | `/knowledge` | FAQ / document corpus |
| Test Bijou | — | Sandbox chat |
| Media | `/api/media` | Images, docs |
| Leads | `/api/contacts` | Captured contacts, CSV export |
| Calls | `/api/call-booking/*` | Bookings |
| Outreach | `/outreach` | Campaigns |
| AI Setup | `/kb-wizard` | Persona + knowledge |
| Settings | `/settings/{email,vertical,calendar}`, `/api/business/profile` | Config |
| Help | `/help` | Support |

**The daily loop:** Home → Inbox (unread) → Escalations (takeover, reply,
resolve) → Knowledge (write the answer so it doesn't escalate again). That last
step is the product's compounding value and is currently the weakest link in
the UI — it requires leaving Escalations entirely.

## Journey gaps — ranked by revenue impact

| # | Gap | Impact |
|---|---|---|
| 1 | Lead capture and registration are separate properties with re-entered details | Every conversion pays a double-entry tax at the highest-intent moment |
| 2 | Supabase SMTP rate limit | Signups fail non-deterministically under load |
| 3 | Two Google flows with different destinations | Inconsistent, unpredictable post-auth state |
| 4 | No email verification screen; no resend-verification UI | Users who miss the email are stuck with no self-service path |
| 5 | Password reset exists (`reset-password.html`) but the landing modal's duplicate-email error only opens WhatsApp | Support load for a solved problem |
| 6 | No billing/subscription UI (`/api/payment/portal` exists, unlinked) | Upgrades require founder involvement |
| 7 | No team/multi-user management anywhere | Single-operator ceiling per tenant |
| 8 | No PDPA data-export or account-deletion flow, though the site claims "PDPA Compliant" | Compliance exposure |
| 9 | Escalation → Knowledge requires a full context switch | The learning loop is friction-gated |

## [PROPOSED] The single highest-ROI change

Collapse stages 2 and 3. Have `OnboardingModal` call `/api/onboarding/signup`
(which already exists, is authenticated, and proxies to the backend) and hand
off with a one-time token instead of a bare link. The user enters their details
once, on the page where intent peaks, and lands already-authenticated on the
QR step.

Prerequisites: fix the `business_name`/`name` mismatch; make `phone` agree
across proxy and backend; custom SMTP so the confirmation email is reliable.
